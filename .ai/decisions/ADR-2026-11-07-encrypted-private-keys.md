# ADR-2026-11-07-encrypted-private-keys

- Status: Accepted
- Date: 2026-11-07
- Scope: the on-disk format of `RsaKey` / `EccKey` private keys in `vn::Crypto`

## Background

Before this, a private key could be exported only as unencrypted PKCS#1 `RSA PRIVATE KEY` or SEC1 `EC PRIVATE KEY`. Traditional DER has no place for a passphrase at all:
it is those numbers. There were only two ways to get "a private-key file with a passphrase":

1. wrap the traditional DER in an encrypted container (PKCS#8 `EncryptedPrivateKeyInfo`);
2. invent a container of our own (a module-defined header plus AES-GCM, say).

The product of option 2 cannot be read by a second program, which trades interoperability for a little convenience and goes against both `G4` (an interface states its semantics) and `G9` (evolvable).

## Decision

**Adopt PKCS#8 + PBES2.** The exact parameters:

- Outer structure: PKCS#8 v1 `EncryptedPrivateKeyInfo`; PEM label `ENCRYPTED PRIVATE KEY`.
- Key derivation: PBKDF2 from PBES2 (RFC 8018), a random 8-byte salt, and an iteration count the caller supplies (200000 by default).
- Encryption: AES-256-CBC (PKCS#7 padding), a random 16-byte IV.
- The input accepts both traditional DERs, RSA and ECC: the backend takes the algorithm and curve identifiers from the key itself.
- The read direction accepts PBES2 plus the older PBES1 / PKCS#12 passphrase schemes, because those parameters are all inside the structure.

API shape (`RsaKey` and `EccKey` each get four methods, all one delegating call):

| Method | Meaning |
|---|---|
| `toEncryptedPrivateDer(password, iterations = 200000)` | Write `EncryptedPrivateKeyInfo` DER |
| `toEncryptedPrivatePem(password, iterations = 200000)` | The same, wrapped in PEM armour |
| `fromEncryptedPrivateDer(der, password)` | Extract the private key from passphrase-protected DER |
| `fromEncryptedPrivatePem(pem, password)` | The same, stripping the PEM armour first |

There is one implementation: `detail::encryptPkcs8Der` / `detail::decryptPkcs8Der` (`src/Pkcs8.cpp`), shared by both key types.

## Rejected options

- **A container of our own (header + AES-GCM + the existing `Argon2`)**: stronger on security (AEAD plus a memory-hard KDF), but nobody recognises the product. The reason to reject it:
  the whole value of a private-key file is that other tools can work with it, and a file `openssl pkcs8` cannot open is a dead end. The module already has `AesGcm` and `Argon2`;
  use those when what is needed is **storing passphrase credentials** rather than a key file, and do not merge the two purposes into one format.
- **PBES1 (the scheme older than PBKDF2) as a write format**: its default iteration count and digest are too weak. It is kept as a **read** capability only, for old files.
- **Fix `iterations` to a constant**: different machines and different threat models need different unit costs, and the parameters travel with the file, so fixing them only puts every
  product on the same compromise point.
- **Overload `toPrivatePem(password)` on top of `toPrivatePem()`**: an overload under the same name would hide the fact that the format changed from traditional DER to PKCS#8
  (`G4`: the name must state its semantics). Changed to `toEncryptedPrivatePem`, whose adjective states the format change outright.

## Consequences

- One new internal file, `src/Pkcs8.cpp`, depending on wolfSSL's `wc_CreateEncryptedPKCS8Key` / `wc_DecryptPKCS8Key` /
  `wc_GetPkcs8TraditionalOffset` (`HAVE_PKCS8`, on by default in this build, so no new CMake option).
- The write path needs an RNG (for the salt and the IV) and reuses the module's existing `detail::RandomHandle`.
- Decryption is **in place**: `wc_DecryptPKCS8Key` writes the plaintext over the ciphertext, so the implementation must copy its input and wipe the copy with `wc_ForceZero`
  before returning.
- A passphrase-protected file is an offline passphrase checker: whoever holds the file can try without limit. Both the documentation and the header say so (`P21` of `.ai/design/crypto.md`).
- The tests prove "what others write, we can read" with fixed fixtures generated by OpenSSL, and "what we write, others can read" by reading this module's output with
  `openssl pkey -passin`.
