# 几何数据的 revision（2026-10-22）：一个对象一条版本号，两次"两级公告"的回退

> B6 的收口记录。结论先行：**每个对象只有一条宿主可写的版本号**，渲染器跟的是几何的那一条；
> `Buffer::revision()` 只对"自己读这块字节"的消费者有效。省带宽那一半仍留在登记表里，触发条件不变。

## 0. 一句话

"粗公告（几何变了）+ 细公告（这块字节变了）"听起来对，但它要求**一个缓存键同时响应两个公告**；
一个数装不下两个公告，折叠就变成哈希。两次尝试都在给这个折叠找名字，最后都变得更复杂。
收回去：**一个对象一条版本号**，谁缓存什么就声明自己跟哪一条。

## 1. 两条注释原本就矛盾（B6 的起点）

| 位置 | 承诺 |
| --- | --- |
| `StreamKey` 的 `revision` 字段 | "来自上游资源（`Geometry::revision()` / `Buffer::revision()`）" |
| `Buffer.hpp` 文件注释 | "缓存了字节的消费者在用之前比一比 `revision()`" |
| `GeometryFacts.cpp`（实现） | 每个通道与索引流都写 `geometry.revision()` —— 只认粗的那一条 |

所以按 `Buffer` 的书面契约公告的宿主，后端看不见：行不会重建（行键是几何 revision），键也不会换。

## 2. 两次尝试，以及为什么都撤回

**尝试一（`a02b9500`，已回退）**：`Geometry::contentRevision()` 返回折叠值（FNV-1a），`StreamKey` 加
`buffer_revision`，行键与命令都改用它。功能上成立（三条用例 + 三个变异都能红），但**名字撒谎**：
`revision` 在这仓库里是"单调计数器"的意思（`setRevision` 的 `@warning` 整段讲只升不降），折叠值不能排序、
不单调，谁把它当版本号存下来就会踩坑。

**尝试二（未提交）**：把折叠藏成私有探测器，公开一个单调计数器（`++` 当折叠变化时）。语义对了，但代价是给
`Geometry` 加两段可变状态 + 每帧每几何一次 O(通道) 检测，而它存在的**唯一理由**是"行键只能是一个数"。
复杂度从"两个事实"漏到了公开面——这一步就是"又搞复杂了"。

**共同的根**：缓存键必须包含它要响应的**每一个**公告。粗公告和细公告是两个事实；一个数装两个事实只能折叠，
折叠就是哈希，哈希穿上 revision 的衣服就是第一次尝试。问题不在命名，在**前提**。

## 3. 现在的规则（一条）

| 谁缓存什么 | 跟哪一条公告 |
| --- | --- |
| 渲染后端：一个**几何的描述**（布局、切片、标量拷贝；GPU 上传按它的通道键共享） | `Geometry::revision()` —— 几何是一个描述，通道集是它的一部分 |
| 几何自己的局部包围盒缓存（读的是**这块字节**） | 它同时认 `(buffer, buffer revision, 段)` 与几何 revision（既有实现，不动） |
| 宿主自己的缓存（拿的是 `Buffer` 的字节） | `Buffer::revision()`，按 `Buffer.hpp` 的说明 |

于是"按 buffer 公告就能让渲染器更新"不再是一份被悄悄无视的契约——三处文档（`Geometry::revision()`、
`Buffer.hpp`、`StreamKey`）现在说的是同一件事，并且点名了各自的读者。

### 3.1 结构变化也不自动公告（2026-10-22 定）

"换了一个 buffer"（`setPositions(new)` / `addBuffer` / `removeBuffer` / `setIndices` / 换切片）几何**看得见**，
但一样**不**自动 `++revision_`，理由不是可见性而是**批量**：宿主编辑一个模型时常常一次动好几条通道
（换 positions、重填 normals、重切 indices），而且刚装上的 buffer 可能还在往里填。只有宿主知道这一批改完没有，
所以公告由它**每批一次**发出，setter 一次都不发。

代价照旧（并且写在 `setRevision` 的 `@details` 里）：**忘喊就是静默的**——渲染器继续画它先传上去的那份。
换来的是"公告点 = 宿主决定的那个点"，而不是被 setter 的调用次序切碎的一串中间态。

## 4. 真要省带宽时，正确的形状（记录，不实现）

把"每通道公告"还给**几何对象本身**，而不是给后端一个派生版本号：

1. `ChannelFacts` 不再急切拷贝标量；上传 miss 时才从 `values->view()` 读（行只负责 layout）。
2. 行键于是只需要"layout 正确"——`Geometry::revision()` 足以覆盖（增加/替换/移除通道是 layout 变化）。
3. 通道键 = `(buffer 指针, 该通道自己的 revision, 段)`；`Geometry::setChannelRevision(location, n)` 让宿主
   指明是哪一条（它不动几何 revision，也不触发重建行）。

这条路**不需要派生版本号**，因为那时行和通道键各跟各的公告，没有"一个数装两个事实"的地方。
前提是先量到带宽真的是瓶颈：今天没有任何宿主报过（16.98 MiB / +30 ms 是构造出来的形状，不是报告）。

## 5. 如果将来做，判据（保留）

- 单通道公告 ⇒ `uploads` 计数只 +1，其余通道键逐字段不变；变异：通道键退回几何 revision ⇒ +通道数，红。
- 几何公告 ⇒ `uploads` +通道数（今天的行为，不能变）；变异：几何公告不再影响通道键 ⇒ 那条用例红。
- 别名范围：两几何同 buffer 同段、几何 revision 相等 ⇒ 一次上传（既有行为）。

## 6. 不做的话

- 带宽那一半保持登记（`graphics-followups-2026-10-19.md` §3.6 的 B6），触发条件不变：宿主报上传带宽。
- 契约那一半**已收口**：文档三处同口径，宿主不再有一份"看起来该生效、实际无效"的承诺。
