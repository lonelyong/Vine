| # | Item | What | Trigger | Source |

| T24 | Invalidation granularity of the scene collection | The invalidation key is still the whole content - the direct path's per-view memo is cleared by the root subtree's `contentEpoch`, the frame path's `SnapshotSource` by `snapshot->revision`: any edit makes every view's list recompute. **Re-measured (2026-11-13, RelWithDebInfo, locally ×3)**: `SelectTest.MeasureWhatOneSelectCostsWithAMovingCamera` - 2000 drawables: pure select 337-340 µs, production miss 435-443 µs; 10000: pure select 2348-3067 µs, production miss 3388-3626 µs. 10k is under the 4 ms gate and 2000 far under the 2 ms line ⇒ **no optimisation**; but 10k itself is already past 2 ms, and the production path costs ~0.9 ms more than a pure select (memo lookup + the shared allocation of 10k commands) - a host that really runs 10k in its daily scenes should look at this half first. | T27 | Re-evaluating the residency trade | the pin model (ADR-2026-11-10) makes residency = what live content needs: content that is off screen but still held by the host no longer yields VRAM automatically. | T30 | Shared backend mechanisms: where the two residency tables live | **The public resource type is settled out of scope, and a backend's count is not what would have decided it** (`../design/graphics-architecture.md` 2.15, and `../decisions/ADR-2026-11-10-gpu-residency-pinned-by-content.md` option D). What remains is a PLACEMENT question about a residency table that has exactly ONE backend consumer today: vk's `ResidencyClaims` (who may BUILD a key — a different question from "may this reserved value be released now"; `ResidencyClaims.hpp` names the difference in its own note). `ADR-2026-11-16` decided where a mechanism both backends use lives (flat in the SDK mainline) **and gave the test**: "their definition is: both backends use it"; `ADR-2026-11-23` D1 replaced that test with "the promise a host can observe", under which `ResidencyClaims` stays plugin-private until this trigger fires. The only part of this that IS public is the ledger (`Residency.hpp`), and it is a VALUE whose four kinds are the host's content model, noted by every backend (`BC-26`, 2026-11-18). **What a second API family would demand of it, measured 2026-11-18**: D3D12 and Metal map the four kinds one-to-one and could measure resource bytes more exactly than either backend does today (heap allocation / `MTLResource.allocatedSize`), and T15's retirement (2026-11-23) is what a Metal backend needs first - Metal has no layout concept at all, so "who transitions" now lives in the backend by construction; WebGPU has neither memory accounting nor residency control, so it would COMPUTE bytes rather than measure them and force a third state beside "counted" and "absent" (`derived`); and `Programs` stays unfillable on every GPU backend (T45). So what is left here is only where the two tables live. **Verified 2026-11-23**: one consumer (`ContentCaches` / `Device` in `gfx_backend_vk`), no SDK header includes the table, and every SDK place that named a plugin unit (`DeviceClock`'s `FrameDriverId` note, `PipelineKey::variant`'s note, three shipped shader comments that named vk's texture set) now states the rule without the name - `check_vk_exposure.py` V6, whose set is derived from the tree, keeps it that way | a SECOND backend needs a residency table of its own kind - then `ResidencyClaims` moves to the SDK mainline; **not** "a third backend exists", and not a second API family on its own | `../decisions/ADR-2026-11-16-no-backend-half.md`, `../decisions/ADR-2026-11-10-gpu-residency-pinned-by-content.md`, `../design/graphics-architecture.md` 2.15, `../decisions/ADR-2026-11-23-retiring-the-reference-backend.md` (D5 records the placement: `ResidencyClaims` moves when this trigger fires) |

| T48 | Re-sharing chunks after a full rebuild | A publication shares a chunk only when no row in it moved, and a row "moved" when its node epoch OR its fold serial changed (review 6, 2026-11-19). A table rebuilt from scratch reports every row as moved - a fresh row cannot claim the same fold answer - so a structural edit (a child added or removed, a state or geometry change) copies the whole table while an incremental edit copies only what it touched. The fix is to carry the previous publication's per-row serials (and the values they describe) into the new rows by identity at the same index, so a row that came back unchanged keeps the number it was published with | a measured full-rebuild publish cost that matters (today: one edit re-folds; a rebuild copies every chunk) | `../design/graphics-frame-pipeline.md` F1 (Caveat) |
| T58 | Alpha-to-coverage for Mask content on a multisampled target | A Mask fragment discards whole fragments, so on a multisampled target its cutout edges keep their pixel steps (`../design/graphics-material.md` F7 N6). `alphaToCoverageEnable` would be the right switch, and it is available directly: the retired backend could not have used it (its render graph pushed its own `MultisampleState` after the application's — `ADR-2026-11-23` D4's amendment), and nothing stands in the way on the shipped path. The mechanism is alpha-to-coverage - ONE switch (`VkPipelineMultisampleStateCreateInfo::alphaToCoverageEnable`, dynamic under the EDS3 floor: `vkCmdSetAlphaToCoverageEnableEXT` + `extendedDynamicState3AlphaToCoverageEnable`) - and it is THREE parts, not one: coverage is derived from the alpha of the fragment's FIRST colour output, and `builtin_forward.frag` writes the drawable's opacity there, so its Mask branch must write the masked alpha when `gl_NumSamples > 1`; the seam must carry "this draw's alpha is a coverage fraction" beside `blend`; and the backend states the switch where it states `blendEnable` (`ContentDraw::recordRasterState`). It CANNOT serve the deferred G-buffer, whose attachment 0 alpha is the occlusion the lighting pass scales. The shader-side `gl_SampleMask` sketch is WITHDRAWN (it existed only for the retired backend's `MultisampleState` override and is a spelling no other API family has), and `T58` is recorded as decided in `ADR-2026-11-23` D4's amendment rather than built | the first real Mask-on-MSAA workload (imported cutout content drawn into a multisampled off-screen target); nothing in the tree draws Mask content at all today | `../design/graphics-material.md` F7, `../design/graphics-rendering.md` F23, `tests/test_vk/MsaaTest.cpp` |
| T64 | Registry identity must not depend on load order | `RenderBackendRegistry::registerFactory` is `factories[name] = factory`: the LAST registration wins and nothing is reported, so a stale plugin silently shadows the backend compiled into the binary (measured 2026-11-23: the replacement segfaulted a plugin-identity case, and only a rebuild told it apart from a regression). `ADR-2026-11-23` decided "keep-first and report the attempt"; **its amendment of 2026-11-25 replaces that shape**: which registration owns a name becomes a **configuration option the host states**, and the item is deferred until a host needs that choice. What the deferral keeps is the invariant - for a given configuration, "which registration owns a name" must be a function of the module identity (name + `VN_RENDER_BACKEND_ABI_VERSION`), never of load order - and the report route the option will need already exists (`RenderBackendRegistry::diagnostics()`, landed with `T65`) | a host has to choose what a second registration of one name does (a plugin overriding the backend compiled into its binary), or the next batch that touches `RenderBackendRegistry.cpp` | `../decisions/ADR-2026-11-23-retiring-the-reference-backend.md` (D5, amended 2026-11-25) |
| T67 | Device-local content streams | `ContentCaches::upload` fills every vertex / index / instance stream into HOST-VISIBLE coherent memory (`detail::createHostBuffer`; `MemoryAllocator::findMemoryType` takes the first `HOST_VISIBLE\|HOST_COHERENT` type and never asks for `DEVICE_LOCAL`), while the other two kinds already follow the device-local rule IN THE SAME MODULE: `ContentImages` allocates an image device-local and fills it through a host staging copy, and a target's attachments are device-local. On a discrete GPU that is a PCIe read per draw for STATIC geometry, and no number in this tree can see it: every measurement so far (the 8.2 ms host run, `T35`'s gate) was taken on a software rasteriser, where the host-visible and device-local TYPE is the same one. The fix is the `ContentImages` shape applied to streams - a host-visible staging buffer plus a `vkCmdCopyBuffer` recorded at the head, published by the same `FrameBuilds::publishAll` evidence, using `BarrierPlan`'s transfer rows so no new synchronisation vocabulary is introduced - plus "prefer a type that is both device-local and host-visible" for integrated / ReBAR devices, which removes the copy on those machines | a measurement on a device whose memory types differ (a discrete GPU), or `T35`'s performance reading being claimed on real hardware - the reading must then name the device and the memory type its streams live in | `../research/graphics-2026-11-25-review-9.md` §3.1 (`K1`), `../design/vk-backend.md` §9.2 |
| T69 | The descriptor-set cache's ceiling is combinatorial and unstated | a content set is cached under the full tuple (screen flag, five views, five samplers, the shadow view and its sampler; swept after 600 frames), so the cost curve is (distinct texture tuples x two layouts) and changing ONE slot rebuilds the whole set; `set_builds` / `sets_live` are the witnesses. The cheap half is an update template or a per-material set with one slot changed; the real answer is a descriptor-indexing (bindless) path, which is a CAPABILITY decision - `VK_EXT_descriptor_indexing` is not required by this backend today - and not a refactor. Today the SDK has five slots and few materials, so `G8` says do not pre-pay; what is missing is the trigger, which is why the first scene that hits the cap would look like a bug | a steady frame whose `set_builds` moves after warm-up, or `sets_live` approaching the pool's `kMaxCachedSets` | `../research/graphics-2026-11-25-review-9.md` §3.8 (`K8`), `../design/vk-backend.md` F9 |

| # | Item | What | Trigger |
|---|---|---|---|
| T17 | Asynchronous upload / compile entry points, and a cold build under the device-wide cache lock | no asynchronous entry (the contract is single-threaded and serial) - and a cold build is worse than "slow in one frame": glslang plus `vkCreateGraphicsPipelines` run inside `resolveFrameHead`'s ONE hold of the content cache's lock, so ANOTHER driver's frame head stalls behind it even when no single load exceeds one frame's budget (review 9 `K5`). ### 2.6 API shape and naming

`T40` (a `FrameContext` for the per-frame hook) landed 2026-11-18 ahead of its trigger
(`../decisions/ADR-2026-11-18-the-frame-carries-its-context.md`) and `T41` (the diagnostics handle's name) landed the
same day. `T42` (a stated per-frame worker) landed 2026-11-22, also ahead of its trigger and on an explicit go:
`PassChain::setOverlayUpdater` states the worker instead of only discovering it on the content, so a controller does
not have to subclass the scene it repaints. `T49` (the screen-program vocabulary) landed the same day, on a go and
because a reader named the mixture: the program path now says `Fullscreen` (`fullscreenCopyProgram`,
`FullscreenCopyChannels`, `drawFullscreenProgram`, `buildFullscreenProgramFacts`, `ContentPipeline::createFullscreen`,
`builtin_fullscreen_copy.frag`), leaving only the backends' private plumbing plus the vk diagnostic codes as `T57`.
`T53` (two names that described a neighbour) landed 2026-11-23, also on an explicit go: `DepthMode` → `DepthPolicy`
(`PassDesc::depth_mode` → `depth_policy`, `RenderPass::depthMode()` → `depthPolicy()`), because a policy is not a state
and the old name sat beside `DepthState`; and `ModelScene` → `SceneBuild`, because the value is what `sceneFromModel()`
built, not a scene (`BC-34` / `BC-35`).
`T56` (one list of declared inputs) landed 2026-11-25 on an explicit go: `PassDesc::inputs` is the one ordered list, an
`ImageInput` states one identity through `byImage` / `byTarget` / `byName` / `byTexture`, and resolution, edges, wiring
checks, the frame table and `Plan::describe` read it (`graphics-rendering.md` 2.13,
`ADR-2026-11-25-one-input-list-per-pass`); `input_names` / `input_targets` are gone.
