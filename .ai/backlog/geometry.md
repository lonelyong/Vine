|---|---|---|---|
| G3 | Solid intersection (a family-level free function) | a consumer that needs it appears. The neighbouring queries are in place but none of them takes two solids: the surface side (closest point, ray × surface, see `../design/geometry-surface-queries.md`) and the curve side (point-to-curve and curve-to-curve distance, see `../design/geometry-curve-queries.md`) are free functions under `requires` constraints, while an analytic solid answers its own ray hits and closest point as virtual members of `Solid<T>` (`../design/geometry-solid.md`), so a solid × solid query has no home to grow in | `../design/geometry-kinds.md` 1.3, 9 |
| G5 | Retire the parametric geometry's B-rep bridge | tessellation is in place (`../design/geometry-tessellation.md`) and no consumer asks for analytic solids any more | `../design/geometry-parametric.md` 2.5 |
| G7 | `TriangleSurface` / `QuadSurface` (the names are reserved) | a single triangle/quad needs queries of its own (ray–face intersection, point-to-face distance); today the free function `intersectTriangle(ray, a, b, c, hit)` serves. When introduced it **must carry the `Surface` suffix** (the repository already has `TriangleMesh` / `QuadMesh`) | `../design/geometry-kinds.md` 2.5 |
| G8 | The fourth derivative of a space curve and the third derivative of an offset | the order rule for an offset is `min(2, base-curve capability − 1)`, so one more order needs the base curve to answer a fourth derivative | a consumer that needs the third derivative of an offset appears (rate of curvature change, higher-order stitching) | `../design/geometry-kinds.md` 2.8, `../decisions/ADR-2026-11-06-space-third-derivative-and-offset.md` |
| G9 | The O(p²) table algorithm for `BSplineCurve` evaluation | splines of degree ≥ 8 land in a batch sampling loop (evaluation is an allocation-free recursive basis function today, and its cost grows with the degree) | `../design/geometry-kinds.md` 2.8 |
| G10 | Temporary allocations in spline-surface evaluation | bulk sampling or evaluation enters a hot path (each call allocates temporary arrays sized by the control-point count today: `deCasteljau` takes its array by value and `differences` returns a fresh one) | `../design/geometry-axis-surfaces.md` 2.5, R2 |
| G11 | Missing combinations in the intersection pair table (ray–line, line–`Aabb`/`Obb`, plane–`Aabb`/`Obb`, `Obb`–`Aabb`) | a consumer needs one of those combinations (booleans, section trimming, a new picking primitive); add it following C1–C4 of `../design/geometry-intersection.md`, without a unified interface | `../design/geometry-intersection.md` §3.1, D1 / D2 |

| G15 | Drop the box's storage scalar to `float` (`Aabb<float>` stored, `double` computed): the box value already is the `min`/`max` of float coordinates, so it is lossless, and after sealing the node box is the largest remaining item | box memory in the picking/query tree of a large model becomes a problem again (sealing has landed, see `ADR-2026-11-10-bvh-seal-and-coarse-picking-tree.md`); first write "storage scalar ≠ computation scalar" into `Bvh` | `../design/geometry-bvh.md` 2.16, 9.2 |

## Criterion reminders

- Every item states a trigger only: a capability without a consumer does not enter the code (`G8`).
- The parametric types are value types, so any new capability has to answer "why can it not be a free function".
